# Boss 机制解析链路

> 状态：active

Boss 攻略由实战视频和解包资源交叉验证。视频负责证明玩家实际看到的前摇、范围、阶段流程和处理方式；解包负责确认 Boss 身份、技能调用、状态、结算 ID 和可明确解释的参数。任何一侧都不能单独替代另一侧。

## 输出与边界

正式输出是 `data/enemies/lc/boss/*.mdx` 中面向玩家的机制说明。中间材料统一放在 `MD/_local/boss-analysis/<地图>/`，包括视频、音轨、转写、截图和证据表，均不得提交。

解包资源只作为证据，不是站点运行时数据源，也不得自动覆盖正文。资源目录名、Ability 名和动画名只能帮助定位，不能单独证明技能表现、触发条件或官方名称。

## 总体链路

```text
地图与稳定 slug
  -> data/enemies/lc/boss/order.json
  -> data/enemies/lc/boss/health-sources.json
  -> 阶段来源 ID
  -> MonsterUniqueIDTable 校验身份
  -> 搜索 BP_AIChar_<阶段来源 ID>
  -> 角色蓝图的能力、被动技能、控制器和行为树
  -> Ability / Device / Weapon / Effect
  -> GAAttackConfigs.SkillId
  -> numerical_config_monsterskill
  -> 与视频时间点和关键帧交叉验证
  -> 人工编写 MDX
```

## 1. 确定范围和身份

1. 从 `data/enemies/lc/boss/order.json` 取得地图内的稳定 slug，不能只按显示名称合并同名 Boss。
2. 从 `data/enemies/lc/boss/health-sources.json` 取得每个阶段的来源 ID。数组顺序就是页面阶段顺序。
3. 使用 `refs/Exports/NZM/Content/DataTables/MonsterUniqueIDTable.json` 校验 ID、名称和形态。
4. 多阶段 Boss 必须分别调查每个来源 ID，不能因为名称相近就复用技能结论。

AIBehavior 资源目录可能沿用旧编号。例如大都会金牌打手的来源 ID 是 `18301061`，但角色蓝图位于 `98301061_RMTubeMan`；Z 博士的来源 ID 是 `18401071`，目录为 `98401071_RMDoctorZ01`。因此应搜索精确的 `BP_AIChar_<来源 ID>`，不能用目录编号猜身份。

## 2. 处理视频证据

1. 读取平台元数据，记录标题、作者、BV 号、发布日期、时长和分 P。
2. 下载视频和音轨到 `MD/_local/boss-analysis/<地图>/`，使用 FFmpeg 合并；原始媒体不得进入 `public/`。
3. 平台没有字幕时，生成带时间戳的本地语音转写。自动转写只负责定位，游戏术语必须回听或通过画面字幕复核。
4. 先按固定间隔生成分镜总览，再对技能前摇、命中和结束时刻抽取关键帧。
5. 为每个 Boss 建立证据表，记录结论、视频时间段、关键帧、解包路径、可信度和冲突。

视频可以直接证明：

- 攻击前摇、方向、范围和场地变化；
- 玩家被命中、击退、限制或获得状态的实际表现；
- 阶段顺序、召唤物和交互装置；
- 视频中实际演示成功的处理方式。

视频不能单独证明未展示难度的差异、精确概率、完整冷却、服务端条件或“唯一正确打法”。UP 主口述与画面冲突时，以可复核画面为准并保留存疑记录。

## 3. 追踪解包资源

从角色蓝图开始，按引用关系调查，不做全仓库名称联想。

### 角色和行为

- `BP_AIChar_<来源 ID>.json`：角色组件、可激活能力、被动技能和附属对象。
- `BP_AIC_*.json`：控制器和默认行为入口。
- `BT/*.json`：技能选择、距离条件、阶段条件和难度分支。
- `BP_AnimProxy_*`、动画配置：只用于确认前摇与 Ability 的对应关系，不能单独定义机制。

### 技能和场地对象

- `Ability/GA_*.json`：技能流程、攻击区域、持续结算、状态标签和 `SkillId`。
- `Device/*.json`：电箱、机关、场地碰撞等交互对象。
- `Weapon/*.json`：投射物或 Boss 手持武器。
- `Effect/`：视觉表现。特效名只能辅助对应画面，不能证明伤害或触发规则。

### 数值结算

`refs/Exports/NZM/Content/DataTables/numerical_config_monsterskill.json` 用 `SkillId` 连接 Ability 与结算行。至少核对：

- `Description` 是否与 Ability 和视频行为一致；
- 结算类型、元素、护盾和暴击规则；
- `HpCalScale`、`HpCalBase` 等字段的实际语义；
- 同一技能是否有普通、强化、引导或持续伤害等多行。

没有完整结算公式和难度语义时，不把 `HpCalScale` 直接写成玩家承受的百分比伤害。

不同资源中的独立字段不能自行拼成因果链。例如交互组件的 `InteractionSpan`、怪物表的 `FallDownDuration` 和电箱破坏 Ability 同时存在，并不能证明“打破电箱后必然倒地指定时长”。只有蓝图或行为树控制流完整贯通，或者视频明确展示该先后关系时，才能写成一个机制流程。组件默认时长也不能直接等同于玩家实际拥有的处理窗口。

任务、对白或提示表可以补充场地机制。例如系统任务明确要求处理某个技能时，可作为命名和交互目的的辅助证据，但仍要与 Ability 和实战表现核对。

## 4. 证据等级

| 等级 | 条件 | 发布规则 |
| --- | --- | --- |
| 已确认 | 视频画面与完整解包调用互相印证 | 可作为确定事实写入 |
| 实战确认 | 视频清楚展示，但解包链未贯通 | 可写玩家可观察行为，不补隐藏条件 |
| 配置确认 | 解包调用完整，但参考视频未展示 | 只写可解释的配置事实，不扩展实战表现 |
| 视频策略 | 视频演示有效的处理方式 | 使用“建议”“可以”等措辞，不写成唯一解法 |
| 存疑 | 只有口述、资源名或相互冲突的证据 | 不发布，保留在本地证据表 |

同一结论至少记录一个视频时间段或一个可贯通的解包调用链。精确数值必须有字段语义明确的配置依据。

## 5. 编写正文

正文优先回答“看到什么、会发生什么、应该怎么做”，内部资源名不进入玩家攻略。根据 Boss 实际机制组织章节，不强制所有页面使用相同标题。

- 主要技能单独成节，先写前摇和危险，再写处理方式。
- 每个技能使用 `**Boss 行为：** ……<br />` 和 `**应对方式：** ……` 两行拆分；行为行只写可观察的触发、动作和结果，应对行集中写走位、转火与交互策略。
- 多阶段形态使用稳定 slug 分页时，在正文开头说明阶段关系。
- 删除只有标题没有内容的占位章节。
- 不编造官方技能名；没有正式名称时使用清晰的描述性名称。
- 视频策略使用建议语气，配置事实使用确定语气，存疑内容不写入正文。
- 不把来自不同对象的配置字段拼接成未经证明的触发、结果或持续时间。
- 页面末尾使用 `Credit` 标注实际采用的视频来源，不大段复制口述。
- 已有正文必须逐条复核后保留、修正或删除，不能整体覆盖用户已验证的内容。

## 6. 单地图验收

每张地图完成后检查：

1. `order.json` 中该地图所有 slug 都有正文；
2. 阶段 ID、角色蓝图和技能目录能够对应；
3. 每个主要机制都有视频时间点或可贯通的解包证据；
4. 没有空标题、无依据精确数值或资源名推测；
5. 来源署名完整，本地媒体和 `refs/` 内容没有进入提交范围；
6. 运行 `pnpm lint` 和 `pnpm build`。
